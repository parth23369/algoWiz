Backtracking Code

function solveNQueens(n) {
  const cols = new Set(), diag1 = new Set(), diag2 = new Set();
  const placement = new Array(n).fill(-1);
  const solutions = [];

  function isSafe(row, col) {
    return !cols.has(col) && !diag1.has(row-col) && !diag2.has(row+col);
  }

  function backtrack(row) {
    if (row === n) { solutions.push([...placement]); return; }

    for (let col = 0; col < n; col++) {
      if (!isSafe(row, col)) continue;      // prune

      placement[row] = col;
      cols.add(col); diag1.add(row-col); diag2.add(row+col);

      backtrack(row + 1);                    // recurse

      cols.delete(col); diag1.delete(row-col); diag2.delete(row+col);
      placement[row] = -1;                   // undo — backtrack
    }
  }

  backtrack(0);
  return solutions;
}

How N-Queens Backtracking Works

N-Queens asks: can you place N queens on an N×N board so that no two attack each other (no shared row, column, or diagonal)? Backtracking solves this by placing queens one row at a time, and the moment a placement becomes impossible, undoing it and trying the next option — instead of generating every possible arrangement up front.

Step by step

  • Work one row at a time. For the current row, try each column from left to right (gold).
  • Check if placing a queen there conflicts with any queen already placed (same column, or either diagonal).
  • If it's unsafe (red), skip this column immediately — this is pruning: never even considering the invalid subtree.
  • If it's safe, place the queen (green) and recurse into the next row.
  • If every row gets a queen, that's a complete solution — record it.
  • If a row runs out of safe columns, backtrack: remove the queen from the previous row and try its next column.

Why backtracking instead of brute force?

Checking every possible placement of N queens on N² squares would be astronomically expensive. Backtracking prunes an entire subtree the instant a placement is invalid — most invalid branches are cut off after just one or two rows, long before wasting time exploring deeper.

Complexity

Time: O(N!) in the worst case (much better in practice due to pruning).
Space: O(N) for the column/diagonal tracking sets and the recursion stack.

When is it used?

  • Constraint satisfaction problems generally (Sudoku, map coloring).
  • Any "place items so no two conflict" scheduling or layout problem.

Compared to other search strategies

  • Backtracking (this): builds a solution incrementally, abandoning ("pruning") a partial solution the instant it can't possibly succeed.
  • Brute force: generates every possible full placement first, then checks validity — wildly wasteful since it explores doomed branches to completion.
  • Dynamic programming: doesn't apply well here — there's no useful overlapping-subproblem structure to cache, since each row's valid choices depend on the entire specific path taken so far.
